# oGMemory M3 QA：上下文与超时诊断

日期：2026-11-01。实验计划、固定配置、验证日志在
`experiments/m3_context_study_20261101/`。
本轮是**固定记忆的 QA 消融**，不是重新生成多模态记忆的端到端复现。

最终共同评分已完成，见同目录`REPORT.md`、`comparison.json`和
`joint_questions.csv`。B两次为0.6077/0.5769，原固定答案重评0.5385；
全部初评分和预测均保留。以下诊断中的独立评分明确属于较早批次，
不能与最终共同评分择高拼接。

## 1. 原因不是数据库检索慢

对原65题的319次QA模型调用，按串行问题次序和逐题模型轮数对齐；
历史用量日志没有问题ID，因此这种对应关系是可检查的顺序重建，
不是原日志自带的字段。本轮 instrumentation 已补上 video/question index。

| 原超时题 | 模型调用累计秒 | 检索累计秒 | 最后一次实际输入 tokens | 节点重复占比 |
|---|---:|---:|---:|---:|
| study_05_Q07 | 207.55 | 1.14 | 120922 | 66.7% |
| study_05_Q11 | 183.04 | 1.59 | 109105 | 46.6% |
| study_05_Q12 | 196.79 | 1.16 | 90008 | 56.8% |
| gym_03_Q03 | 191.87 | 1.69 | 115008 | 63.2% |
| bedroom_04_Q05 | 197.59 | 1.42 | 105055 | 55.7% |
| bedroom_04_Q10 | 229.92 | 1.27 | 108458 | 60.6% |

节点重复率不等于传输字节重复率；逻辑API耗时可能包含内部重试。
全部题的输入峰值156689，累计19905749 tokens。首轮约1250 tokens，
随后多个 Search 返回 description、转写、事件、人物、实体的完整对象，
不同查询间的重叠片段反复进入历史。一轮还可能调用不止一次 Search。

`core/react_loop.py` 原180秒是在下一轮开始时检查，不会自动终止正在执行的HTTP请求。
五道超时题在准备进入第六轮时被拦住，另一道在第五轮前被拦住；
有些成功题最后一轮跨过180秒仍会返回答案。这是原来的软截止语义，
不能把它描述成严格的180秒墙钟上限。

## 2. M3-Agent 可借鉴的机制，以及不能照搬的地方

参考本地 `m3-agent/m3_agent/control.py` 与 `m3-agent/mmagent/retrieve.py`：

- 参考控制协议一次生成一个 Search 查询，通常按clip取少量结果；
  当前同模型适配配置为top-k=2。
- 控制器持有 `current_clips`，已经交付过的片段不会在后续普通
  clip-wise Search 中重复展开；identity专用memory-wise分支另有逻辑。
- 返回的是记忆图中的短文本事实，带人物身份/语义关系，不是我们的
  description + events + entities 等完整episodic JSON。
- 最后一轮明确要求回答。原参考提示允许合理猜测；oGMemory新收尾
  **不采用这个要求**，证据不足必须说明。

不能直接把我们top-k改成2就认定等价：

- 两边记忆粒度和人物关联不同；
- oGMemory的精确邻居用于补全动作顺序、代词和局部转写，不能随意全部去掉；
- 有预算裁剪时，“检索到了”不代表“模型已经看过”，不能仅按节点ID永久排除；
- 必须保留账号/视频/时间范围，不能为了缩短上下文引入未来记忆。

## 3. 本轮实施

### 3.1 复用已有预算模块，而非重新发明

仓库原本已有 `m3/context_budget.py`，正式五视频基线为保持旧流程没有启用。
本轮A组显式启用，使用与之前历史验证一致的本地代理tokenizer，
而不是粗暴截取字符串：

1. 服务器约束检索条数、候选数、返回节点总数和搜索调用数。
2. 跨查询按内容版本去重，正文只出现一次，其余位置引用。
3. 原文抽取式选择，优先description和相邻转写，不额外调用LLM总结。
4. 每轮重新建立预算内视图；所有引用只指向本轮实际保留的证据。
5. 原始记忆、完整工具结果及审计不被裁剪视图覆盖。
6. 计数包括整个消息历史与工具schema，预留8192输出和2048安全空间。

原文边界和时序必须保留，明确提示“遗漏不是事实不存在”；
计数题不能把被检索/入选的事件数冒充全视频总数。

### 3.2 有限时间内保留回答机会

`m3.qa_context.answer_reserve_seconds: 45` 是新增可选配置，默认0保持兼容：

- 剩余时间不足“45秒 + 最近一次模型耗时”时关闭Search；
- 最后一轮也只开放Answer，而不只是文字上要求停搜；
- 模型忽略schema时，服务端仍拒绝Search，不加轮、不伪造答案；
- 只保留有依据的回答，允许明确说证据不足；
- 压缩时保留无新增证据与检索关闭的指导信息；
- 一次极慢HTTP仍可能超时，因此是提前收尾而不是硬取消保证。

如果实际实验没有触发时间预留，只能证明最后一轮收尾有执行记录，
不能把全部超时改善归功于45秒机制。A/B分开正是为了辨别这一点。

### 3.3 更准确的诊断

- `context_calls`：打包前剩余时间、模型耗时、打包CPU耗时、可见片段数、
  可见新增片段数、已执行Search数量、选择的源节点和原文范围。
- `finalization_reason`：时间预留或最后一轮；与QA最终成功/失败分开。
- 修复通用trace只读取 `name` 而漏掉provider的 `tool` 字段的问题；
  执行逻辑不变，后续trace能正确记录Search/Answer。
- 可见新增原文范围目前只是诊断，未擅自替换现有no-gain策略。

## 4. 实验边界

- A：输入估计上限22528，旧收尾；
- B：同样输入预算，加入回答收尾和guidance保留；
- C：输入上限12000，其余同B；额外trace修正只影响诊断，不影响提示。
- D：同C的12000预算，已选原文按字段分组，减少JSON包装；
  不改写原文，hash保留在审计，仍需独立质量验证。

四组不重新生成记忆、不按算法失败挑选最好重试、逐组冻结源码。
分数来自同模型自动评委，不是独立人工准确率；该五视频是开发样本。
输出预算8192不变，避免通过减少推理预算掩盖“只有reasoning没有答案”问题。
历史与当前服务负载/缓存不同，观察到耗时降低不等于严格的架构加速比。

本轮优先控制上下文和运行稳定性，尚未解决视觉前缀采样遗漏、
人物跨片段身份关联、记忆事实本身错误等上游问题。

## 6. 不要把总token缩减等同于费用缩减

A恢复后65题全部回答，独立/恢复评分0.5538；这是共同重评前的结果。
与原固定答案的历史共同评分0.5462相近，不能据此宣称质量提升。

| 用量口径 | 原固定答案轨迹 | A恢复后固定轨迹 |
|---|---:|---:|
| 总输入 | 19,905,749 | 4,722,001 |
| 缓存输入 | 12,987,771 | 724,155 |
| 未缓存输入 | 6,917,978 | 3,997,846 |
| 缓存比例 | 65.2% | 15.3% |
| 逻辑QA调用 | 319 | 359 |
| 输入峰值 | 156,689 | 16,904 |

总输入下降76.3%，未缓存输入下降42.2%，调用次数反而增加。
额度失败的额外11次旧轨迹调用（其中10次未收到usage）单独保留，
不假设它们没有产生任何计费用量。

代码上，每轮依据当前问题/查询重选原文，会改变较早的工具结果；
这与稳定前缀较短、实际缓存比例降低的观察一致，但不是对供应商缓存机制的
控制实验。M3-Agent的普通clip检索则只追加未返回过的片段知识。
下一阶段可以研究前缀更稳定的增量证据交付，但不能为了缓存而永久排除
“曾被检索、却没有真正交付”的事实，也不能把已移出的正文当作仍在上下文里。

## 7. 当前semantic consolidator不是可直接替换的紧凑语义层

再次核对 `oGMemory/m3/semantic_memory_consolidator.py`：

- 它按片段顺序拼接description（最多50,000 UTF-8 bytes），并对人物、事件、
  实体做集合式合并；不是LLM生成的高层简洁事实或可查询身份等价关系。
- 源节点列表和SUPPORTS/EVOLVES边可追溯整个聚合，但不能直接当成
  每条事实都具备独立的可用时间和状态变化历史。
- 当前QA默认检索 `episodic_memory_generator`，没有把整视频聚合MemoryNode
  当作M3-Agent式人物/语义事实索引消费。

因此，直接把整视频聚合塞进QA会重新引入大上下文，还可能把问题时间之后的
信息带进来。更合理的下一阶段是：按来源与可用时间索引细粒度事实，
区分稳定存放位置/偏好与当前观测状态，显式维护人物身份及物体关联，
再按需展开相邻原片段。需要单独验证，不能把这一设计建议写成已完成能力。
