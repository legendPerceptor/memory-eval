## 结论

**值得移植其中的并行调度和资源保护，但不宜整包直接替换当前实现。**
它能增加同一时间在途的远端请求数，正好针对当前主要耗时；不会自动降低单次
MiniMax多模态请求的服务端耗时。当前已经是4路片段并发，不能把从串行到32路
LoCoMo的收益直接外推到本实验。

正确实现的独立任务并发不必改变问题、证据与推理过程，但这不等于保证每次分数相同。
PR同时包含模型切换、整段视频输入、失败容忍和检索降级等行为变化；这些不属于
纯调度优化，必须与并发变量分开评测。

## 1. 哪些改动直接相关

| PR模块 | 实现 | 对本轮的意义 |
|---|---|---|
| `m3/_parallel.py` | 有界线程池、按输入顺序返回、异常收集、线程局部模型实例 | 可作为片段/问题并行的基础；默认8个worker |
| `m3/episodic_memory.py` | 独立片段生成并行 | 当前只有1–4路配置，可移植为可调4/8路；不改模型和帧输入 |
| `m3/qa.py`、`m3/eval.py` | 每线程独立控制器，问题/评分并行 | 独立问题可并行；同一题的Search→Answer仍需顺序执行 |

| `m3/voice_asr.py` | 线程局部ASR实例 | 并发会增加模型副本及显存需求，不应在T4上直接套用8/32路 |

## 2. 基于本轮真实耗时的估算

已完成的新增视频study_09，79片段/12题：

| 阶段 | 实测分钟 |
|---|---:|
| oGMemory完整构建 | 62.89 |
| 其中远端情景记忆生成 | 55.29 |
| 来源事实索引 | 0.26 |
| oGMemory QA | 12.23 |
| M3记忆阶段 | 45.05 |
| M3 QA | 5.27 |
| 两方法合计，不含最终共同评分 | 125.70 |

**以下仅是理想调度估算，不是实测提速或时间承诺：**
假设每次API延迟不因并发增加、无RPM/TPM/计划额度限制、无额外失败和资源争用，
将记忆生成4→8路、QA 1→4路：

- 只改oGMemory：约88.88分钟，即总耗时减少约29%，约1.41倍吞吐提升。
- 两方法都同步调整：约62.40分钟，即接近总耗时减半、约2.01倍吞吐提升。

后一个估算把M3整个记忆阶段都简化为可并行，略为乐观。
M3参考适配位于外层 `comparisons/m3_agent_matched/`，不是该PR修改的模块；
仅合并PR不会自动把我们M3适配的4路记忆生成和串行QA也加速。
其他视频的帧数、题数、请求时延不同，不能直接乘十作为准确ETA。

PR描述中的LoCoMo32路结果与“2–3天→3h57m”属于作者报告，未在本机复现；
M3的0.601与旧单视频0.267还涉及视频集合和模型配置变化，不能据此证明并行既提速又提分。

## 3. 可能影响准确率或评测可信度的地方

### 应保持不变的纯并行边界

- 固定MiniMax-M3.1-Flash、adaptive/medium、输出预算、提示和检索参数。
- 固定每30秒收集30帧、同一规则选16帧，保持完整音频和时间边界。
- 独立片段/独立问题并行，但不要在记忆未完整构建时开始QA。
- 每题独立控制器、上下文、证据去重集合和截止时间；输入与输出按ID匹配。
- 维护固定分母、原始失败记录和来源哈希；不按返回顺序把评分分配给题目。

### 不应作为纯加速一起引入的改动

1. `deploy/ogmemory.m3.yaml`切换为kimi/glm/deepseek分工，并采用不同输出预算和embedding模型。
   这些会改变实验条件，不能用于本轮同模型对照。
2. `--use-video`向模型发送整段视频，改变输入模态和观察方式；不等价于16帧配置。
3. `m3/voice_asr.py:334–345`及`m3/pipeline/stages.py:897–925`默认容忍约15%的音频失败。
   例如79片段时可容忍11个ASR失败；`max(1, ...)`还意味着非空输入即使比率设为0仍可能容忍1个。
   这有可用性价值，但“流水线完成”不再代表完整语音证据，应单列覆盖和缺失，不称无损提速。
4. `retrieval/seed_retriever.py`在embedding故障时降级为BM25/root路径，候选证据可能改变。
   这是通用检索路径，不能未验证就断言本轮M3专用控制器一定经过它。
5. span抽取允许部分失败/丢弃滞后结果；以及文本写入的语义merge并发，均需单独验证内容完整性
   和顺序影响。写锁/CAS能改善一致性，但不证明LLM语义合并对顺序不敏感。
6. 高并发若造成限流、重试、排队或GPU OOM，会间接改变有效覆盖率和180秒软预算内能完成的轮数。

### 与当前分支整合时的额外风险

- PR在anttrail基础上，当前分支已有上下文预算、来源事实、严格增量、收尾策略和30帧修正。
  只读三方合并预览出现15个带冲突标记的文件；不代表所有自动合并部分都语义兼容。
- PR的`m3/qa.py`线程局部adapter构造没有我们新增的
  `context_budget=load_context_budget(args.config)`；移植时必须保留，不能覆盖掉E方案。
- 本轮M3适配自行实现QA，并有共享缓存及随机种子；不能只用线程池包住现有循环就认定线程安全。
- 当前用量审计以进程环境变量传递video/question标签；同进程多线程QA会产生标签竞态。
  必须改为线程/上下文局部标记或进程隔离，同时维持全局额度保护。
- PR共享worker参数涵盖远端LLM和本地ASR，video-workers又会乘上每视频并发。
  embedding semaphore也是进程内限制，不是跨所有视频的总限制。
- `parallel_clips`收齐整个列表才返回；QA/judge调用方随后才写JSONL。
  因而中断可能丢失已计算但尚未落盘的答案，应增加逐题完成日志/检查点而非仅依赖有序汇总。
- PR调整工具重试usage为只统计接受的响应。分析真实费用应保留每次请求的用量，
  包括已消耗token但结果未被采用的重试；不能把少记用量当成降成本。

## 4. 本次实际验证

在独立源码导出目录运行，没有调用付费LLM，也没有写实验数据库：

- 正确工作目录下，选定并行、视频调度、人脸聚类、QA接线、评委、embedding、检索和schema测试：
  **147 passed**；仅有pytest缓存目录权限警告。
- 评估模块设为单worker：**38 passed**。
- 但一个依赖顺序的端到端mock测试存在不稳定性：8路下单测重复10次，**3次通过、7次失败**。
  该测试使用共享的按调用顺序弹出分数队列，以及有状态的脚本式LLM；并发完成顺序改变后
  无法保证指定题号得到预设分数。它说明测试替身需要按问题键控或线程隔离，
  **不能据此断言真实MiniMax会把别题的答案/分数串到当前题**。
- 最初从外层目录执行还遇到一个测试使用相对YAML路径的失败，改到PR源码根目录后消失；
  首轮日志也保留，没有只保留通过结果。
- 未做真实MiniMax并发1/4/8的质量/延迟A/B，未重跑PR声称的LoCoMo和M3成绩。

原始测试、只读合并预览、耗时推算与源码在 `runs/pr300_review_20261102/`；
轻量验证回执见 `docs/pr300_parallel_review.json`。

## 5. 建议的移植和验证次序

1. 不改变正在运行的十视频协议；先在独立开发分支做性能候选。
2. 优先移植连接池/DDL保护、并发工具、线程局部QA adapter及独立评分并行；
   保留本分支现有预算、采样、失败口径、MiniMax配置和共同评分。
3. 先把两方法远端记忆的**全局**并发目标设为8，QA从2路验证到4路；
   本地ASR先维持1路，CV维持小并发。不要叠加video-workers后无意变成16/32/64路。
4. 使用已经完成的视频及固定记忆验证QA并行：比较完整率、问题/证据/来源哈希、
   时间越界、调用次数、延迟分位数、重试/429、输入量和共同评分；另设串行重复估计自然波动。
5. 记忆生成并发4/8需用相同媒体、独立结果目录重新生成小规模样本，检查记忆覆盖及答案差异；
   无法仅靠固定记忆QA实验验证记忆构建阶段的并发效果。
6. 验证通过后，把加速配置作为新实验版本；若需要中途切换，必须明确切换边界并分组报告，
   不把混合配置的总耗时标注为单一配置的性能。
